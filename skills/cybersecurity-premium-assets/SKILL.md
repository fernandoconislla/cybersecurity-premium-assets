# Cybersecurity Premium Assets

## Contract
**Two inputs:** `nombre` (required, non-empty) and `descripcion` (optional). Both values originate **only from the user**. When `nombre` is absent and the user wants to generate an asset, ask for the name; optionally offer a small input screen with required name and optional description. When the user only asks for ideas, propose concepts without treating the proposal as a submitted input. **Never invent or auto-populate `nombre` or `descripcion` and present them as user-supplied.** If `descripcion` is omitted, autonomously choose a sensible visual composition as an internal design decision; keep the input truly absent. A description may change composition, but never override hard rules. Report conflicts.

**Output:** an original, genuine editable SVG `assets/<slug>.svg`, **rendered visibly and directly in the response as an image** (not just described), plus a working download link to the real SVG file. PNG may be a QA preview only, never the substitute deliverable. Verify actual SVG and preview paths exist and the image renders successfully before offering downloads. **A file path printed as text is NOT a visible image; Markdown/image component must display the actual preview.** Only mark as approved after explicit user approval.

## Hard rules
1. Canvas `width="1024" height="1024" viewBox="0 0 1024 1024"`. Background fully transparent.
2. Exactly three global CSS tokens in `<style>`: `--PRIMARY: #092B60;`, `--SECONDARY: #38BDF8;`, `--CONTRAST: #FFFFFF;`. All painted shapes use `.primary`, `.secondary`, or `.contrast` classes reading `var(--TOKEN)`. Values may later change for rebranding; the roles must not change.
3. No fourth colors, gradients, shadows, filters, patterns, opacity effects, raster images, external artwork, or background rectangle. Whites must be internal and enclosed by stronger colored surfaces for visibility on white backgrounds.
4. Main subject's dominant visible dimension ≈ 90% (922 units, tolerance ±2%). Preserve aspect ratio, center *both* axes; keep equal geometric margins on the minor dimension and avoid clipping. Optical offsets of up to 12 units require justification.
5. Use **all fourteen approved, immutable references**: `assets/escudo-candado.svg` (shield/lock), `assets/base-de-datos.svg` (database V2), `assets/servidor.svg` (server), `assets/firewall.svg` (firewall V3), `assets/api-key.svg` (API KEY V3), `assets/cloud.svg` (Cloud V2), `assets/persona-simple.svg` (Persona Simple V3), `assets/hacker.svg` (Hacker V4), `assets/organizacion.svg` (Organización V1), `assets/router.svg` (Router V3), `assets/switch.svg` (Switch V3), `assets/malware.svg` (Malware V12), `assets/antivirus.svg` (Antivirus V4), and `assets/laptop.svg` (Laptop V1). They define the family together: smooth Bézier curves, deep navy outer contours, restrained enclosed white divider, cyan/navy flat field split, clear focal subject, consistent detail density. Do not attach shields/locks to unrelated concepts or clone the database silhouette.
6. Geometry must consist of independently editable paths/shapes, logically grouped and identified. Never modify **any approved reference** as a side effect. Design new assets as fresh files.
7. Verify at 1024, 128 and 64 pixels on white and visually compare side by side with **all** approved references. The icon must read as the named concept without labels.
8. **Color-layout decisions must be justified, never mechanically copied:** All three palette tokens remain globally defined and no fourth color may be used, but splitting an object into cyan/navy halves is **not mandatory**. Decide whether to split based on the concept's geometry, legibility and perceptual benefit. Whenever choosing either **split** or **uniform fill**, state that choice and its specific rationale to the user in the visual audit. If the split is merely decorative, do not use it. A uniform cyan field can retain primary navy outlines and contained white detailing, thereby using the full palette without an arbitrary division.

## Mandatory evidence-based visual-reference research (before drawing)
1. **Search the internet before generating each NEW asset.** Research real, recognizable icons in official design systems and product iconography relevant to technology, IT and cybersecurity; prioritize official sources such as IBM Carbon, Microsoft Fluent, Google Material and Lucide, plus actual cybersecurity/identity product semantics when relevant. Search broadly enough to obtain at least **three genuinely distinct visual precedents**; do not invent reference names, descriptions or images.
2. **Inspect and compare** the found references by concept semantics, technical/cybersecurity fit, immediate recognizability, silhouette orientation, composition, simplicity at 64 px and suitability for our premium family. Show a concise evidence-backed comparison with working source links and explicitly identify the winning reference, its strongest alternatives and why it wins. If research is unavailable, disclose that honestly; do not claim research occurred or fabricate citations.
3. **Semantic precision:** a user/avatar is not automatically an authenticated user; a shield, key, badge, lock or network detail changes the concept. Differentiate router vs Wi-Fi, organization vs org chart, malware vs generic software bug. Use technical standards for semantics and premium references for geometric refinement as separate evidence. Avoid extra motifs unless the supplied `nombre` or `descripcion` warrants them. Use industry-standard metaphors rather than imaginary novelty.
4. **Original vector reconstruction:** inspect and reinterpret the reference's *concept, orientation, silhouette, curve quality, proportions, detail hierarchy and repeated-element count*, without copying protected path data. User-provided imagery takes precedence and may guide a close formal reinterpretation through original vector paths. Build independent, editable geometry, respect source licensing and the immutability of our existing approved assets. User-provided image references take precedence for intended silhouette unless the user explicitly asks for a new researched direction.
5. **Iterate before the approval gate:** compare the candidate with the user-provided or winning reference, the preceding version, and every approved master. Track accepted and rejected geometry; fix critical visible defects prior to seeking approval. If incremental edits do not improve the design, rebuild fresh original SVG geometry instead of patching. Fix visible design defects, run the SVG validator and inspect at 1024/128/64. Never invent tests, scores, downloaded paths or visual assessments. Explain the design decisions (including split vs uniform fill) and remaining limitations.

## Workflow
1. Read **all** approved SVG references and these rules, accept `nombre` plus optional `descripcion`, and complete the **mandatory external reference research and comparison** above before selecting a geometry.
2. Select the most recognizable visual metaphor without unnecessary decoration. Build real vector geometry with only the three token classes.
3. Normalize the visible bounding box to 922 dominant units, center in both axes without distortion; audit optical balance separately. If symmetry is required, construct mirrored pairs and verify exact limb/arrow counts, placement, spacing and orientation.
4. Run `python scripts/validate_asset.py assets/<slug>.svg`. Any failure blocks output. Inspect real 1024px renders for curves, tangencies and connections, 128px for visual hierarchy, and 64px for silhouette, semantics and noisy details. Compare all approved masters together and add a matching-size reference/prior-version comparison.
5. Perform TWO mandatory independent audits: technical (hard invariants) AND visual-design (criteria below), with separately reported visual **reference fidelity** and **relative family color distribution** where relevant. Fix critical defects and re-audit; technical success cannot override visual failure, and a high average cannot conceal a critical failure.
6. **Mandatory visible media gate:** render the **actual candidate image visibly inline in the current user-facing response**, ideally at 1024px on white, using a real embedded image/preview component linked to a generated verified path. Do not substitute plain text paths, quoted `sandbox:/...` strings, an external placeholder, a generic image lookup, or Markdown source as if those were a rendered preview. Provide visible 128px and 64px previews and a visible comparison sheet including **every current approved master**; link the actual validated SVG file with a clickable download link. Confirm the exact preview and SVG files exist in the active container/session before linking. If a preview does not render, **repair display and re-render before continuing**; never describe an invisible preview as shown. Report both audits transparently and label **candidate** until explicit approval.
7. **Mandatory interactive approval gate (imperative, no plain-text substitution when functional controls are available):** Immediately after the candidate's **visible inline image**, working SVG download, comparisons and audit, ask **«¿Apruebas este asset?»** and render an actual **interactive form** with precisely two selectable decisions: **«Aprobar e incorporar a GitHub»** and **«Solicitar una nueva optimización de diseño»**. Use state-bound radio-group (or equivalent), initialized safely to `optimizar`, and a real confirm/submit button. **Only when `optimizar` is selected**, dynamically reveal a blank multiline optional `textarea` labelled **«Indicaciones adicionales (opcional)»**. When selected decision is `aprobar`, hide the textarea; clicking confirm must submit approval of the exact file/version/hash reviewed, not guessed paths. When `optimizar` is selected, the same real submit button sends the version, the user's additional text (or no text if blank), preserved/rejected constraints, identified audit issues and explicit **no-publication** instruction. In ChatGPT's available interactive UI, use controlled `radio-group`, conditional `textarea`, and `button` wired synchronously to `GenUI.issueNewTurn(...)`, or the actual equivalent host action. **Do not use static Markdown checklists, printed choices, text-field placeholders, a copy-only button, inert controls or ask the user to type a stock phrase in place of the working form.** No invented third option; new concept/regeneration belongs under optimization with optional user guidance. Fall back to conversational choice **only if the environment genuinely cannot render functional interactive controls**, and explicitly disclose that technical limitation. The approval control applies strictly to the currently visible candidate. Explicit plain-text user approval also remains valid without reconfirming.

8. On **approval**, verify the candidate file exists and its actual SHA-256 matches the approved version; publish the **exact approved bytes**, not a reconstruction or substitute. Verify the Git blob, update the catalog, and check prior approved SHAs unchanged. On optimization, log accepted/rejected/preserved decisions, compare altered curves/details between versions, rerun the validator and both audits, then repeat the approval gate. Never accept a rejected design as approved.
9. **Automatically return to the beginning after successful publication:** after confirming BOTH that the approved SVG exists on GitHub and that the skill/catalog update succeeded (while previous approved masters remain unchanged), display a **real functional interactive form** for the next asset, with controlled input **`nombre` required** and textarea **`descripcion` optional**, both initially **blank**, plus a functioning submit button that sends the user's actual field values to the next turn. Ask the user which asset to make next. Do not reuse the previous asset name/description and do not start new generation until the user submits the new input. If any publication step fails, do not show a misleading completed cycle—report the failure and resume verification/repair first. Do not confuse the new-asset screen with the preceding approval decision screen.

## Mandatory visual-design audit
Evaluate each category separately with an evidence-based 0–10 score and a concrete finding:
1. **Concept recognition:** verify meaning even at 64px, distinguish the technical concept from generic icons, and identify alternative readings or unwanted semantics created by extra motifs.
2. **Premium refinement:** audit Bézier tangencies, contour continuity, curve smoothness, optical alignment, corners, extremity endings, white-border thickness and intentional negative space; do not award high scores automatically.
3. **Composition and hierarchy:** coherent focal point, intentional negative space, no competing decorations.
4. **Geometry and volume:** verify plausible connections, overlaps, separation lines reaching their intended edges, no floating components or accidental containers. Check the precise count, orientation, direction and spacing of repeated elements; if symmetry is required, confirm geometric mirroring, not just approximate appearance. For stacked forms, separations must visibly join lateral edges.
5. **Optical balance:** perceived mass and left/right distribution, beyond mathematical centering.
6. **Visual-family consistency:** compare with **all** approved masters for contour hierarchy, enclosed white divider, relative color dominance, curve quality, density, optical scale and whether the new icon appears noticeably heavier/darker/more illustrative. Match the graphic language, not either icon's silhouette.
7. **Color-role composition and explicit decision:** only approved tokens, contrast on white, and independently assess relative cyan/navy/white visible area, cyan surface prominence when meaningful, and white-border weight against **all** masters; reject excessive visual dominance unless semantically justified. Cyan is often the main surface but not a mandatory percentage. Avoid artificially split color regions and unrelated extra containers. **Mandatory disclosure:** write a short section **«Decisión cromática y justificación»** stating **«División cromática: Sí/No»**, why it materially improves (or fails to improve) geometry, meaning, hierarchy or volume, and the trade-off. Explain this *before* asking for the user's approval. Absence of the explanation fails the design-audit process.
8. **Small-size readability:** inspect actual 128px and 64px renders, ensuring the silhouette and semantic landmarks survive, without tiny teeth, lettering, overlapping terminals or internal lines turning into noise.

**Mandatory verdict:** READY FOR USER APPROVAL / REQUIRES REVISION / TECHNICALLY INVALID. **Additional visual criteria, scored independently 0–10:** (9) **fidelity to a supplied/winning reference** (proportions, curves, orientation, parts, angle and details; use N/A with reason if no comparable reference); (10) **family-relative chromatic composition** (relative fill areas and visual weight, not only valid hex codes). A critical failure of reference fidelity, count/orientation, recognizability, continuity or family consistency BLOCKS approval-readiness until corrected. A design failing recognizability, layer continuity, or family consistency is REQUIRES REVISION, even when technically valid. Scores are qualitative and must not be invented as test results. Document concrete deficiencies even if average score is high; failing one critical criterion cannot be masked by an average. Include actionable changes prioritized by impact; never assert user approval before explicit user decision.

**Design lesson from database V1 → V2:** an identifiable silhouette alone does not pass review. If separators float or decoration competes with the primary concept, simplify and reconnect the geometry before presenting a candidate.

**Design lesson from firewall V1 → V3:** correct conventional orientation is essential: a firewall is typically represented by a horizontal brick wall, not a narrow vertical panel. The wall should fill the available canvas proportionally rather than leave excessive vertical negative space, while preserving the dominant-dimension normalization rule. The flame should sit directly at the center of the wall, not inside an unrequested circular badge. Assess silhouette, negative space, placement and concept-specific composition before approving.

**Design lesson from Cloud V1 → V2 (approved):** copying the cyan/navy vertical split onto every object is not family consistency. For a continuous cloud silhouette the vertical seam does not improve recognition or volume and detracts from minimalism. Uniform cyan surface with navy outer contour and enclosed white border is the approved solution. Every new candidate still requires an explicit split-versus-uniform decision and justification, without assuming Cloud's treatment works universally.

**Design lesson from API KEY V1 → V3:** keep established semantic imagery but prioritize clear textual meaning when the user specifies it (API rather than a generic code symbol). Diagonal orientation can significantly improve square-canvas utilization; maintain horizontal letter baselines for legibility even when the object is diagonal. Simplify internal teeth and microdetails before approving. Verify that letters remain real editable vector paths, never embedded raster or font-dependent text.

**Design lesson from Persona Simple V1 → V3 (approved):** when the asset name is generic, research recognized real-world iconography before proposing a novel metaphor. A simple person is best represented by a separate circle head and rounded symmetric shoulders. Avoid mistaking a generic avatar for authenticated user, administrator or protected identity. Keep the silhouette clear at 64 px; no superfluous lock/shield. User-supplied reference imagery and researched official design-system precedents take priority over unnecessary creative reinterpretation. A cyan uniform fill is justified because a central split has no semantic value.

**Design lesson from Hacker V1 → V4 (approved):** reference research supports a hooded figure with a frontal laptop as a recognizable hacker metaphor, while still noting that this convention is not a neutral depiction of every cybersecurity professional. Avoid helmet-like or overly pointed hoods: use a rounded, compact crown and a clearly bounded face opening. Prioritize the laptop silhouette and a bold minimal terminal mark at 64px. The color division follows meaningful components, not an arbitrary center line; explain this in every audit.

**Design lesson from Organización V1 (approved):** for organization as an institution or enterprise, a conventional building conveys entity identity better than people/group or hierarchy symbols. Do not confuse an institution with an org chart. Symmetrical stepped building geometry and moderately spaced windows remain recognizable at small scales. Distribute color by semantic building components (cyan façade, navy outer outline and entrance, contained white border and windows), and explain why a split would not help.

**Design lesson from Router V1 → V3 (approved):** for technical network routing, prefer the conventional circular routing node with four arrow directions over a home Wi-Fi router unless a physical wireless device is explicitly requested. When users provide a specific visual reference, privilege its form and curves while independently constructing original SVG `<path>` elements—never substitute an AI-generated PNG for the requested editable SVG. Four separate Bézier arrow paths, an enclosed white ring, navy routing hub and uniform cyan disc read at 64px. Do not claim exact geometric fidelity to a source SVG that has not been retrieved. Validate all three SVG CSS roles and the 922px normalization, inspect actual renders and request explicit approval before publication.

**Design lesson from Switch V1 → V3 (approved):** a topology switch is distinguished from a router by a square rather than circular body. Four independent arrows must not be replaced by three double-headed arrows or redirected per row. Under the approved reference, both left-column arrowheads face left and both right-column arrowheads face right, preserving four separate physical paths and gaps visible at 64px. Orientation and count are primary semantic geometry, not decorative details: compare the actual source icon before scoring fidelity. Use uniform cyan field, navy arrows and outer contour, and an enclosed white separator; no artificial color division.

**Design lesson from Malware V1 → V12 (approved):** the user-provided premium diagonal cyber-insect image established the technical-insect metaphor, but the final approved icon is deliberately a *vertical symmetrical beetle* (three legs per side, two mirrored antennas). A centered white skull on an uninterrupted cyan abdomen makes malware semantically clearer than a generic bug; the skull must **not** have its own badge/container. The broad rounded abdomen avoids resemblance to a shield, and thinner carefully proportioned limbs limit navy dominance. Do not reinstate files, electronic circuit tracks, arbitrary asymmetric limbs, skull containers, or earlier abandoned concepts. In visual critiques, inspect the real SVG at 1024, 128 and 64 pixels and compare actual colors and the precise approved silhouette, not just technical-rule compliance.

**Design lesson from Antivirus V1 → V4 (approved):** after initially exploring a shield with check, then a magnifier with a blocked bug, the user's chosen visual metaphor was a **single shield with a single check**. Premium finish comes from redesigned, continuous Bézier crown/shoulder contours, balanced shape, uniform cyan field, navy exterior/check and a restrained enclosed white separator. The user explicitly rejected excess elements in V2 (magnifier, insect and extra badge) and preferred the shield/check approach. Do not mechanically reuse the geometry of `escudo-candado.svg`: consistency in outline language is not permission to clone an approved master. Preserve approved V4 exact SVG and SHA-256; user approval is binding on its bytes.

**Design lesson from Laptop V1 (approved):** a generic laptop should be recognizable as a standalone open portable computer rather than be confused with Hacker V4's frontal laptop component. Three independent visual zones suffice: large cyan display, restrained white bezel within a navy enclosure, and a perspective keyboard deck with two bold simplified keyboard indicators. The frontal bottom lip must not become dominant, and micro-key details must not be added if invisible at 64px. No unrequested badges, security symbols, locks, terminal marks, brand logos or arbitrary vertical cyan/navy splits. Preserve the exact approved SVG with SHA-256 `39dbba9976feac236ea74605f78e8953eb3ac7c41ac3818dc8b2196458141fbf`.

## Consolidated design decisions and eight quality improvements
The following operational checks consolidate the 30 lessons across reference research, original editable SVG construction, premium curve quality, family coherence, iterative audit and safe publication; where the core rules above already cover a topic, this section supplies the enforcement procedure rather than repeating the rule.

1. **Conditional optimization notes (new UI):** selecting optimization exposes a blank optional multiline instructions field; approval hides it. A functional submit action forwards exact version, notes (or blank), blockers and preserve/change constraints. No invented user `descripcion`.
2. **Independent reference fidelity audit:** compare original/reference and candidate at comparable orientation and apparent size; audit number/direction of parts, proportions, anatomy, line thickness, Bézier curves and fine details. A user-provided premium reference is the primary visual target, while new SVG paths must remain original.
3. **Independent family chromatic audit:** explicitly compare cyan, navy and white visual dominance, white divider thickness and the relative filled areas across every master. A shared palette does not automatically imply shared visual identity.
4. **Symmetry verification:** when bilateral symmetry is required, generate mirrored paired elements or algorithmically compare their geometry; detect mismatched numbers, shapes and gaps rather than trusting optical centering.
5. **Repeated-element count and direction verification:** record and inspect exact positions, orientation, number, gap and direction of each repeated part. Never invert switch arrows or alter insect leg count contrary to the source or user specification.
6. **Critical-defect approval blocker:** mark REQUIRES REVISION, correct and rerun both audits before presenting approval when semantic fidelity, composition, connection, required direction/count, readability or family membership fails, regardless of numeric average.
7. **Versioned accepted/rejected decision log:** for every redesign track `Preserve / Change / Reject / Verify`, including source (user, reference or audit); visually compare precise modified regions against the prior candidate. When an approach stalls, rebuild original SVG geometry instead of accumulating patches. Never revive previously rejected motifs.
8. **Between-version detail comparison:** enlarge modified Bézier joins, end caps, line widths, anatomical transitions and high-contrast interior marks; audit 1024/128/64 to confirm improvements survive reduction and avoid noise.

**Nonnegotiable cycle controls:** the genuine SVG is the primary artifact (PNG only QA), with precise centered 90% bounds and exclusively three parametrized colors; no unrequested shield, badge, file or frame; no floating pieces, disconnected separators or excessive embellishment. Keep actual verifiable SVG and rendered previews, record SHA-256, publish only exact approved bytes, preserve original Git blobs, then display **blank** new-asset inputs. Run this skill automatically for every new generation, edit, optimization, audit or publication in this family, even when not explicitly requested.

## Final response quality gate — MUST PASS before sending
This check is **imperative** for every new or optimized candidate; the user must not be asked to repeat a request because the assistant omitted the interface:
1. **Real file evidence:** candidate SVG was actually saved in the active session, verified on disk, hashed, and passed the official validator. Never infer its existence from a past turn or show a fabricated sandbox link.
2. **Visual delivery:** a full-size actual preview appears **visibly inline**, not as a printed filesystem path; 128px and 64px images are also visible; a family-comparison image is visible. If the image rendering fails, fix it before continuing.
3. **Download delivery:** link a real clickable SVG file whose exact path was verified this turn. PNG previews do not replace it.
4. **Two audits:** show validator evidence and independent visual audit including color-role rationale, reference fidelity, family consistency, small-size legibility, and critical defects.
5. **Working approval form:** show a usable stateful two-choice form with a real submit button, conditional blank optional instructions textarea visible **only** for optimization, and actions scoped to exact candidate/version/hash. The button must cause the advertised next action, not just copy text.
6. **No premature completion:** if any of checks 1–5 fails, do **not** state "skill complete", "PASS", or "READY FOR USER APPROVAL". Repair the missing deliverable/control before sending; if technical limitations cannot be resolved, report precisely which step is blocked without pretending the full workflow was executed.
7. **Post-publication separate gate:** only after exact-byte GitHub publication, approved-skill update, and verification of all older masters, display a different **empty new-asset input form**. Never confuse it with the candidate-approval form or show it while the candidate remains unapproved.

## Learned operational safeguards
- **Source of truth and freshness:** Fetch the latest `SKILL.md`, the approved SVGs and validator from GitHub **at the start of each new request**; do not rely on cached instructions, a prior conversation or a made-up installed skill version. Also verify reference candidates on their official external websites at generation time.
- **Distinct user inputs vs design decisions:** `descripcion` absent means absent, not an assistant-composed description. A proposed concept is not a confirmed `nombre`.
- **Approval is scoped and binding:** associate user approval with the exact candidate bytes/filename shown; only publish those bytes, not a reconstruction. On interrupted publication, check GitHub first and resume the original confirmed action without changing the design.
- **Evidence, not decorative previews:** visually embed actual renders at 1024/128/64 and the current full-family contact sheet; never leave the user with printed file paths rather than visible images, generic image-search substitutes or inert approval controls. If preview or interaction fails, disclose the issue and fix it before seeking approval.
- **Two independent gates:** technical validation must genuinely be run, not inferred from visually plausible markup; visual design audit must be critical rather than automatically assigning 9+/10.
- **Traceable publication:** after explicit approval, check GitHub fetch result and report the published path. Confirm master-file SHAs unchanged; update skill/catalog only after successful asset publication.
- **Closed-loop UX:** after successful publication AND skill/catalog verification, show fresh empty fields for `nombre` and optional `descripcion`. Each successful publication ends at the beginning of a new cycle, awaiting the user's next submission.
- **Minimalism:** remove features that do not help identification (floating decorative bands, gratuitous status indicators, competing top-edge details). Avoid treating reused colors as sufficient evidence of family coherence.

## Never rationalize violations
- More detail never permits a fourth shade or gradients.
- Changing geometry must not alter color tokens; rebranding must not alter geometry.
- PNG embedded in SVG is not a vector asset.
- Square canvas is not proof of correct 90% scale: test the visible bounding box.
- An attractive standalone icon is not necessarily part of this family: compare side-by-side.
- If a renderer cannot resolve CSS tokens, use a temporary **validation-only** copy with colors resolved; keep the SVG original parametrized.
